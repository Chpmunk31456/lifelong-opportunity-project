## United States — O*NET-SOC 15-1252.00
O*NET describes Software Developers as researching, designing and developing computer/network software or specialized utility programs; analyzing user needs and developing solutions; updating or enhancing software; integrating software with hardware where applicable; and maintaining application-area databases or coordinating database development.

Current tasks include analyzing user needs and feasibility; developing/directing testing, validation and documentation; collaborating on system limitations, interfaces and performance; modifying software to correct errors or improve performance; planning installation/modification; and manipulating data to analyze system capabilities and requirements.

### Preparation

- **85% bachelor's degree**;
- **5% associate degree**;

These are occupation-level responses and are not universal hiring rules for every Software Developer vacancy.

## Canada — NOC 21232
Canada Job Bank maps Software Developer / Software Programmer to **NOC 21232 — Software developers and programmers**.

Job Bank describes the occupation as designing, writing and testing code for new systems/software, creating software-system foundations and running diagnostic programs to verify effectiveness. Workers are employed across software/game-development firms, IT consulting and IT units across sectors.

### Requirements and regulation
Current Job Bank requirements state that a bachelor's degree in computer science/software engineering or another discipline with significant programming, **or** completion of a college program in computer science/related field, is usually required.

Job Bank currently identifies NOC 21232 as **not regulated in Canada**. Employer requirements can still vary by role, sector and seniority.

### Wages
Current national wages, updated November 19, 2025:

- low: **C$30.00/hour**;
- median: **C$48.08/hour**;
- high: **C$76.92/hour**.

### Outlook
Job Bank's current national 2024–2033 projection says labour demand and labour supply are expected to be **broadly in line**. Current three-year provincial/territorial prospects vary: for example, Ontario and Saskatchewan are Limited, Nova Scotia is Good, and many other provinces are Moderate. Readers should verify the specific region rather than assuming one short-term national rating.

## Professional / authority boundaries
A Software Developer should not:

- deploy to production without assigned authority/change process;
- bypass code review, CI gates or security controls merely to meet a deadline;
- place credentials, keys, tokens or secrets in source/public repositories;
- copy production customer data into personal/local/demo systems without authorization;
- change authorization controls to make a feature “work” without approved requirements;
- perform intrusive security testing outside explicit scope/permission;
- treat test success as proof of defect-free or secure software;
- claim legal, accounting, clinical, safety or regulatory conclusions outside assigned expertise;
- use employer proprietary code/data in a public portfolio;
- merge/deploy AI-generated code without understanding, review and testing.

## Secure-development boundary
The revised guide should include defense-in-depth concepts such as validation, safe data handling, authentication/authorization, secrets management, dependency management, logging/monitoring, secure defaults, code review and testing. Exact controls depend on architecture and employer governance.

NIST SSDF and OWASP resources can support learning. They do not grant permission to attack or penetration-test systems.

## Privacy/accessibility boundary
Developers should minimize protected/personal data, follow approved access/retention rules and avoid logging sensitive values unnecessarily. Accessibility responsibilities depend on product/context but may include keyboard use, semantic structures, labels, focus, contrast, error handling and assistive-technology compatibility. Automated checking does not prove legal compliance.

## Responsible AI
Policy-approved AI may help explain code, draft functions/tests, refactor, create synthetic data and draft documentation. Controls must include:

- no protected source code, secrets, credentials, private customer data or unreleased information in unapproved AI tools;
- human review/understanding;
- actual compilation/execution/tests;
- review for invented APIs/packages, insecure logic and incorrect assumptions;
- dependency/license review where required;
- no autonomous production deployment outside governance;
- AI output is not itself execution evidence.

## Safe portfolio guidance
Use self-built, open-source, explicitly licensed or demo software and synthetic/public data. A strong portfolio can show requirements, architecture choices, source control history, tests, API/data work, secure configuration, CI, documentation and a controlled demo deployment.

Do not publish employer source code, customer data, credentials, private infrastructure, internal endpoints or unauthorized vulnerabilities.
